# Доступ пропал — что делать

## Чем это оказалось 14 августа 2026

Разбор сделан, причина найдена и устранена. Она оказалась не той, о которой
думали.

**Настройка SSH была полностью в порядке.** Порты 22, 443 и 2222 подняты
через `ssh.socket` — правильный способ для Ubuntu 24.04, — в `ufw` все три
разрешены, ключ `do-agents` принимался. Ломать там было нечего.

**Сервер задыхался от нехватки памяти.** Из 7.8 ГБ было занято 7.3 ГБ, свап
на 2 ГБ забит под завязку, `load average` доходил до 148 при двух ядрах —
это не нагрузка на процессор, а дисковая молотилка от свапа. OOM-killer ядра
убивал процессы прямо в момент диагностики.

Съедали память серверные части редакторов: **5.1 ГБ из 7.8**. У пользователя
`admin` одновременно работали и `.vscode-server`, и `.cursor-server`, у второго
пользователя `winpc` — свой `.vscode-server`. Каждое новое окно редактора
оставляет на сервере свои процессы, и сами они не убираются. За 13 дней
накопилось 28 таких процессов только у `admin`.

**Почему это выглядело как поломка SSH.** TCP-соединение принимает ядро, без
участия sshd. Отвечать дальше должен sshd — но в свап-молотилке он не успевал
получить процессорное время за отведённые секунды. Снаружи выходило ровно то,
что видел пользователь: «соединение есть, но это не SSH». Отсюда же и ложный
вывод, будто sshd повесили не на тот порт.

### Что сделано

| Изменение | Зачем |
|---|---|
| Убито 28 накопившихся процессов редакторов | Освободило 1.7 ГБ сразу |
| Свап 2 ГБ → 8 ГБ | Пики больше не упираются в потолок |
| `OOMScoreAdjust=-900` для `ssh.service` | Ядро убивает sshd последним — доступ не теряется |
| Установлен `earlyoom` | Разгружает раньше, чем система встанет колом |
| `MemoryHigh=3G` на каждого пользователя | Один пользователь больше не съест всю машину |
| Команда `free-editors` | Разгрузка вручную одной командой |

Свободной памяти стало 4.5 ГБ вместо 2.2 ГБ, свап почти пуст, 12 подключений
подряд по обоим портам прошли за 1.0–1.4 секунды.

### Если повторится

Признак тот же: «соединение есть, но это не SSH». Проверьте память — через
Web Console DigitalOcean или обычным входом, если SSH отвечает:

```
free -h; uptime
```

Мало свободной памяти и `load average` в разы больше двух — выполните:

```
free-editors
```

Команда снимает накопившиеся серверные части VS Code и Cursor; при следующем
подключении они поднимутся заново. Чтобы не копилось: держите один редактор,
а не VS Code и Cursor одновременно, и время от времени делайте
`Remote-SSH: Kill VS Code Server on Host`.

## Порядок действий

### Шаг 1. Запустить диагностику на Mac

Откройте Терминал и вставьте одну команду — она скачает скрипт в папку
с ключами и сразу запустит его:

```
cd ~/Downloads/SERVER-MAC && curl -fsSL https://raw.githubusercontent.com/bondarenky-star/151eye/cursor/restore-ssh-access-vscode-96cf/server-access/mac-setup.sh -o mac-setup.sh && chmod +x mac-setup.sh && ./mac-setup.sh
```

Запускать нужно из папки распакованного архива — рядом должна быть папка
`keys/` с ключом `do-agents`. Если `cd` ругается `No such file or directory`,
значит архив распакован в другое место: найдите папку `SERVER-MAC` в Finder
и подставьте её путь.

Ошибка `chmod: mac-setup.sh: No such file or directory` означает ровно одно —
скрипт ещё не скачан в текущую папку. Команда выше это и делает.

Скрипт сам проверит порты 22, 443 и 2222, поймёт, кто виноват — сервер
или ваша сеть, — пропишет рабочий порт в `~/.ssh/config` и настроит VS Code.
В конце он напечатает вердикт и сохранит лог на Рабочий стол
(`server-diagnostika.txt`).

Если в конце написано «ГОТОВО» — переходите к шагу 3.

### Шаг 2. Если скрипт сказал чинить сервер

Доступа по SSH нет, значит идём через аварийный вход:

1. https://cloud.digitalocean.com → Droplets → `agents-s-2vcpu-8gb-160gb-intel-sfo3`
2. Вкладка **Access** → кнопка **Launch Web Console**
3. Откроется окно терминала прямо в браузере, вход как `root`
4. Вставьте блок из `console-paste.txt`

Web Console работает через панель DigitalOcean, а не через SSH, поэтому она
доступна всегда — даже когда sshd на сервере полностью лежит.

После этого вернитесь на Mac и запустите `./mac-setup.sh` ещё раз.

### Шаг 3. Подключиться из VS Code

1. Закройте VS Code полностью — **`Cmd` + `Q`**, а не крестиком.
   Иначе он не перечитает настройки.
2. `Cmd` + `Shift` + `P` → `Remote-SSH: Connect to Host` → `do-agents`
3. `File` → `Open Folder` → `/home/admin/projects`

## Что означает каждая ошибка

Диагностика делит все случаи на пять, и лечатся они по-разному.

| Что видно | Что это значит | Где чинить |
|---|---|---|
| `Connection refused` | Сеть до сервера в порядке, но sshd не запущен | На сервере |
| Тишина, `Operation timed out` | Пакеты дропаются: ufw, бан fail2ban или ваш провайдер | Зависит от шага 2 |
| `Connection timed out during banner exchange` | TCP соединился, но SSH не ответил. **Чаще всего сервер перегружен и sshd не успевает ответить** — реже на порту не тот сервис | На сервере: сначала `free -h; uptime` |
| `Permission denied (publickey)` | Сервер жив и слышит вас, но не принимает ключ | На сервере (`authorized_keys`) |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | Устаревший отпечаток в `known_hosts` | На Mac (скрипт чистит сам) |

Ключевое различие — между «refused» и «тишиной». Отказ означает, что пакет
дошёл до сервера и тот честно ответил «здесь закрыто». Тишина означает, что
пакет кто-то съел по дороге: фаервол, бан или сеть.

## Четыре причины, из-за которых это ломается чаще всего

### 1. Серверу не хватает памяти

Именно это и было 14 августа. Подробности — в начале файла. Проверка:
`free -h; uptime`. Лечение: `free-editors`, затем `server-memory-fix.sh`.

Отличить от настоящей поломки SSH просто: если сервер перегружен, соединение
то проходит, то нет — с одного и того же компьютера, без всяких изменений
настроек. Сломанный порт так себя не ведёт, он не работает всегда.

### 2. Порт 443 добавили, но он не заработал

В Ubuntu 24.04 sshd по умолчанию стартует **через systemd-сокет**
(`ssh.socket`). В этом режиме порты берутся из настроек сокета, а строки
`Port` в `sshd_config` **молча игнорируются**. То есть классический рецепт
«допиши `Port 443` и перезапусти ssh» здесь просто не работает — при этом
никаких ошибок не показывается.

А если следом отключить `ssh.socket`, не включив `ssh.service`, SSH
пропадает вообще — и на 443, и на 22. Ровно то, что вы описываете.

`server-repair.sh` и блок из `console-paste.txt` переводят SSH в обычный
режим службы, где `Port 22` и `Port 443` работают как ожидается.

### 3. ufw не пустил 443

Фаервол на сервере по умолчанию открывает только 22. Если sshd повесили на
443, а `ufw allow 443/tcp` не сделали, снаружи будет глухая тишина.

### 4. fail2ban забанил ваш домашний IP

Сервер стоит на публичном адресе, его постоянно перебирают боты, и fail2ban
включён. Если вы несколько раз подряд попробовали зайти с неправильным
ключом или на мёртвый порт, ваш адрес мог попасть в бан. Снаружи это выглядит
как «сервер умер»: полная тишина, никаких ошибок.

Ремонтный скрипт снимает все баны.

## Если и после ремонта тишина

Проверьте **облачный фаервол DigitalOcean**: панель → Networking → Firewalls.
Он работает *до* сервера, поэтому изнутри его не видно, и `ufw` на него никак
не влияет. Если там нет правила на 443 — добавьте.

Проверьте, режет ли ваша сеть порт 22:

```
ssh -T -o ConnectTimeout=10 git@github.com
```

Ответ вида `Hi username! You've successfully authenticated` или
`Permission denied (publickey)` означает, что 22-й порт наружу проходит —
GitHub ответил. Если команда просто виснет, ваш провайдер или VPN режет 22,
и работать нужно только через 443.

## Полезные команды

С Mac:

```
ssh do-agents                  # обычный вход (порт подставит config)
ssh do-agents-443              # принудительно через 443
ssh -v do-agents               # с подробностями, если не пускает
ssh do-agents 'uptime; who'    # проверить, что сервер жив
```

На сервере (в Web Console или после входа):

```
systemctl status ssh.service
ss -tlnp | grep -E ':(22|443)'
ufw status
fail2ban-client status sshd
journalctl -u ssh.service -n 50 --no-pager
```

## Что делает `mac-setup.sh`

- находит ключ `do-agents` и проверяет, что он не побился при передаче
- вычищает устаревшие отпечатки сервера из `known_hosts`
- перебирает порты 22, 443, 2222 и определяет живой
- сравнивает с контрольными подключениями к GitHub, чтобы отделить проблему
  сервера от проблемы вашей сети
- переписывает блок `Host do-agents` в `~/.ssh/config` под рабочий порт
  и добавляет запасные псевдонимы `do-agents-22` и `do-agents-443`
- прописывает в VS Code и Cursor платформу Linux, путь к SSH-конфигу
  и увеличенный таймаут подключения
- ставит расширение Remote-SSH, если его нет

Существующие записи других хостов в `~/.ssh/config` не трогаются, а копии
всех изменённых файлов сохраняются рядом с суффиксом `.backup`.
